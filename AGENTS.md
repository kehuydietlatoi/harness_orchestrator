# Project memory (canonical — read by ALL harnesses)

> **Write convention:** record durable project facts HERE, not in native harness memory.
> **Work loop:** `orch next --agent <you>` → work in the printed worktree → `orch submit`.
> **Review:** when `orch review-queue --agent <you>` is non-empty, review the other harness's PRs.

## Conventions
_(add project-specific facts, gotchas, and architectural decisions below)_

- **Batched issue lookups**: `eligibleIssues` (`src/board/board.ts`) and `reviewQueue` (`src/board/review.ts`) resolve dependency/PR issue state from a single `listIssues({state:"open"})` result indexed by `byNumber(...)` — never a per-dep/per-PR `getIssue`. An issue absent from that open-issue map (closed, missing, inaccessible) is treated as non-blocking / skipped, matching the old `openDeps` semantics. Keep new hot-path issue lookups on the batched map; reserve `getIssue` for single-target paths (`checkMergeGate`, `resolvePrIssue`).
- **GitHub list pagination** (`src/github/github.ts`): `listIssues`, `listOpenPrs`, and `listLabels` page through `gh api repos/{owner}/{repo}/<issues|pulls|labels>` (`page`/`per_page=100`, looping until a page comes back short) instead of a single `gh issue|pr|label list --limit N` — those subcommands take only one `--limit` with no offset, so a fixed number silently truncates past that count. This means list reads use REST JSON shapes (lowercase `state`, `head.ref`, label/assignee objects) mapped by dedicated `parseRest*` functions, distinct from the GraphQL shape (`--json ...` on `gh issue/pr view`) used by the single-target `getIssue`/`getPr` and parsed by `parseIssue`/`parsePr`. The `/issues` REST endpoint also returns PRs (flagged via a `pull_request` key) — `listIssues` filters those out to match `gh issue list` semantics.
- **Claim-lock lifecycle** (`refs/orch/lock/issue-<n>`): a lock is released on exactly these paths — successful merge (`src/board/review.ts`), claim-setup rollback (`src/tasks/service.ts`), a failed/no-commit run (`processNext` in `src/tasks/runner.ts`), and `orch abandon <n>` (`src/commands/abandon.ts`). Any new terminal state for a task must release the lock and prune its worktree, or the issue becomes un-reclaimable.
- **Run telemetry**: every completed `processNext` harness run appends exactly one best-effort record to `~/.orch/<project>/runs.jsonl`. Missing/malformed logs and telemetry IO errors must yield null usage or a warning without changing the task outcome.
- **Board projection**: `buildSnapshot` (`src/board/snapshot.ts`) is the canonical read model for open tasks. Keep GitHub/Git/telemetry reads in that module and add derived board fields to its pure `assemble(...)` helper so terminal, JSON, and dashboard consumers share one mapping. `Snapshot.reviewQueue` contains PR numbers carrying `review:needed`.
- **Dashboard boundary**: `src/server/server.ts` serves the read routes `GET /` and `GET /status` (`/status` calls `buildSnapshot` in-process) and the write routes `POST /actions/suggest` (runs the judge in-process, writes nothing, `502` on judge failure), `POST /actions/assign` (`applyPlan`→`editIssue`, adds `assigned-by:brain` when `origin:"brain"`), `POST /actions/plan-preview` (pure `parseTickets`/`resolvePlan`, writes nothing, `400` on an invalid draft), and `POST /actions/plan-create` (`createIssues`, `400` on blocking errors). `assign` and `plan-create` are the two mutating routes; suggest/plan-preview write nothing. Every `/actions/*` request passes the `isLoopback` chokepoint before any side effect, and `startServer` still binds only `127.0.0.1`. Trust is locality-only (no token); a future off-box tunnel MUST add a token check in that one chokepoint first. See ADR-0004. Keep the read routes byte-for-byte stable when touching this file. `GET /status` resolves its board through the injectable `ServerDeps.snapshot` seam (defaults to `buildSnapshot`, so normal-mode bytes are unchanged); `orch serve --demo` passes a fully in-memory `ServerDeps` from `src/server/demo.ts` so the dashboard runs with no `gh`/git/`claude` — swapping only the I/O boundary, never the routes or `applyPlan`/`selectUnassigned` logic.
- **Effort routing boundary**: task effort is the abstract tier `easy | hard`, mapped through each adapter's `models` config before invocation. `RunContext.model` carries the resolved agent-specific value and affects `runTask` only; review invocations do not receive model flags.
- **Assignment routing boundary**: plain `orch assign` emits a whole-open-graph routing brief for issues missing both `agent:` and `effort:` labels; `--apply` is fill-blanks-only and never replaces either existing routing label. Keep lead judgment external and assignment planning pure in `src/routing/assign.ts`; `--round-robin` is the legacy eligibility-gated path. Both routing writers (`orch assign` and the dashboard `POST /actions/assign`) call `ensureLabels(labelDefs(...))` (`src/github`) before `--add-label`, so a repo whose GitHub labels predate a label-set addition (e.g. `effort:*`, `assigned-by:brain`) **self-heals** instead of failing the write; `orch doctor` also flags any missing canonical labels. Label creation stays additive — never destructive.
- **Planning boundary**: `orch plan` is four modes over one pipeline. Bare `orch plan` (the default) hands the terminal to an **interactive** `claude` session (`spawnInteractive`, stdio inherited, `src/util/spawn.ts`) seeded via a single-line `--append-system-prompt` (`formatInteractiveSeed` — no newlines/quotes/backticks, for argv safety) carrying the absolute output path; the session writes `tickets.json`, which orch reads back (**file-handoff**, detected by mtime) and validates with `resolvePlan`. `ensurePlanSkill` installs the skill first so the contract is present. `--draft "<goal>"` runs the LLM planner (`runPlanner`, `src/tasks/planner.ts`), which reuses the judge's shared headless spawn (`runHeadlessAgent` + `lastFencedBlock`, `src/adapters/headless.ts`) and is fail-closed (non-zero/timeout/unparseable/empty/invalid all throw → nothing created). `--dry-run` and create share the pure split in `src/tasks/plan.ts`: `parseTickets` (structural + field-type — array-of-objects shape, and any present `id`/`title`/`body` must be a string, `dependsOn`/`files` an array of strings; malformed values are collected ticket-indexed and thrown together, never silently filtered or coerced) → `resolvePlan` (the single semantic validator: **errors** block creation — missing title, duplicate id; **warnings** are advisory — unknown/self dependency dropped, file-ownership overlap) → `createFromPlan` (refuses on errors). The ticket contract lives once in the `orch-plan` skill (`assets/skills/orch-plan/SKILL.md`): inlined into the `--draft` prompt for determinism (never relying on headless skill auto-discovery) and installed by `orch init` as an interactive `/orch-plan`. `runPlanner` and `runJudge` both route through the lead's `hard` model tier.
- **Judge evaluation boundary**: `evaluatePlan` (`src/routing/judge-eval.ts`) is the single definition of a *contract-valid* routing plan — `coverage-missing`, `coverage-extra`, `duplicate`, `invalid-agent`, `invalid-effort`, `missing-rationale`. It is pure (no IO/model) and shared by three consumers: the deterministic golden tests (`test/judge-eval.test.ts`), the opt-in live-model gate (`ORCH_JUDGE_LIVE=1`), and the `orch assign --judge/--auto` completeness warnings (stderr, so piped plan JSON stays clean). `applyPlan` stays the *write-time subset* — it drops malformed entries as skips but is structurally blind to a forgotten issue and to rationale quality, which is exactly what `evaluatePlan` adds. Routing *quality* (not just validity) is an offline telemetry replay, designed in ADR-0005, not implemented. See also `docs/judge.md`.
