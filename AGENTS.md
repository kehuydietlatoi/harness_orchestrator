# Project memory (canonical — read by ALL harnesses)

> **Write convention:** record durable project facts HERE, not in native harness memory.
> **Work loop:** `orch next --agent <you>` → work in the printed worktree → `orch submit`.
> **Review:** when `orch review-queue --agent <you>` is non-empty, review the other harness's PRs.

## Conventions
_(add project-specific facts, gotchas, and architectural decisions below)_

- **Subprocess I/O (`src/util/exec.ts`)**: every external call goes through `exec`, which always uses `shell: false` + an argv vector (no shell/command injection; `commandExists` passes the name as a positional `$1`, never interpolated). `exec` buffers combined stdout+stderr up to `DEFAULT_MAX_BUFFER` (64 MiB, overridable per call via `opts.maxBuffer`); on overflow it kills the child and returns a **non-zero** code with a `maxBuffer` note rather than silently truncating output a parser would misread. Callers that only read `stdout` on success are unaffected; anything relying on full output of a genuinely huge command must raise `maxBuffer` deliberately.
- **Security / threat model**: task content (issue/PR bodies, diffs, review comments) is **untrusted input to the agent** — prompt injection is an accepted, review-backstopped risk bounded by *who may author issues/PRs*, not by any sanitization `orch` performs. `orch` does not sanitize task content; the boundary is authorship + cross-review (ADR-0003) + human merge. See ADR-0007; revisit it before ever accepting issues/PRs from outside the team.
- **Logging vs. stdout output**: `src/util/log.ts` is the leveled logger for **diagnostics** (`log.error|warn|info|debug`) — it writes to **stderr** so a command's machine-readable stdout (board/status/snapshot JSON, `--draft` plan JSON, judge plans piped to files) stays clean. Route warnings/errors and verbose tracing through it; keep genuinely user-facing command output on `console.log` (stdout). Level comes from `ORCH_LOG_LEVEL` (`silent|error|warn|info|debug`, default `info`) and is overridden by the global `--verbose`/`--quiet` flags via a `preAction` hook in `cli.ts`; `cli.ts`'s `wrap()` error boundary and the top-level rejection handlers all emit through `log.error`. Tests redirect output with `setLogSink`. Not every `console.*` is migrated — the `src/commands/*` presentational output is intentionally stdout.
- **Test tiers & coverage**: `npm test` runs the fast mocked unit suite; `npm run test:coverage` adds v8 coverage with **regression-ratchet thresholds** in `vitest.config.ts` (set just below the current baseline — raise them as coverage climbs, never lower them to make a change pass). Coverage excludes `src/cli.ts` (wiring, covered by e2e); the low overall number is the thin, intentionally-un-unit-tested `src/commands/*` layer. CI runs `test:coverage` + `test:e2e` on Node 20 and 22 across Linux and Windows.
- **Build & run (`src/` → `dist/`)**: the `orch` bin is `dist/cli.js` (compiled), not `src/`. The global `orch` is typically `npm link`ed to this repo, so **after editing `src/` you must `npm run build`** before the global command reflects the change — otherwise it silently runs stale compiled code (and a long-lived `orch serve` process must also be restarted to reload it). For iteration without a build, run `npm run dev -- <args>` / `npm run orch -- <args>` (both `tsx src/cli.ts`). `public/index.html` is served from source at runtime, so **frontend-only** edits show up without a rebuild (hard-refresh the browser). A `prepare` script auto-builds on `npm install`/`npm link`; `files` publishes `dist` + the runtime assets the CLI reads relative to its module (`public/`, `assets/`, `tickets.example.json`). The `test/e2e/*.e2e.ts` smoke suite (`npm run test:e2e`, separate `vitest.e2e.config.ts`, excluded from `npm test`) compiles and runs the built `dist/cli.js` as a subprocess — the one guard against a broken build / stale dist that the mocked unit suite can't see.

- **Batched issue lookups**: `eligibleIssues` (`src/board/board.ts`) and `reviewQueue` (`src/board/review.ts`) resolve dependency/PR issue state from a single `listIssues({state:"open"})` result indexed by `byNumber(...)` — never a per-dep/per-PR `getIssue`. An issue absent from that open-issue map (closed, missing, inaccessible) is treated as non-blocking / skipped, matching the old `openDeps` semantics. Keep new hot-path issue lookups on the batched map; reserve `getIssue` for single-target paths (`checkMergeGate`, `resolvePrIssue`).
- **GitHub list pagination** (`src/github/github.ts`): `listIssues`, `listPrs`/`listOpenPrs`, and `listLabels` page through `gh api repos/{owner}/{repo}/<issues|pulls|labels>` (`page`/`per_page=100`, looping until a page comes back short) instead of a single `gh issue|pr|label list --limit N` — those subcommands take only one `--limit` with no offset, so a fixed number silently truncates past that count. This means list reads use REST JSON shapes (lowercase `state`, `head.ref`, `merged_at`, label/assignee objects) mapped by dedicated `parseRest*` functions, distinct from the GraphQL shape (`--json ...` on `gh issue/pr view`) used by the single-target `getIssue`/`getPr` and parsed by `parseIssue`/`parsePr`. The `/issues` REST endpoint also returns PRs (flagged via a `pull_request` key) — `listIssues` filters those out to match `gh issue list` semantics.
- **Claim-lock lifecycle** (`refs/orch/lock/issue-<n>`): a lock is released on successful merge (`src/board/review.ts`), claim-setup rollback (`src/tasks/service.ts`), successful `orch abandon <n>` cleanup (`src/commands/abandon.ts`), and failed/no-commit runner recovery only after safe cleanup actually removes the worktree (`processNext` in `src/tasks/runner.ts`). Failed/no-commit runs, successful merges, plain abandon, and repair use safe worktree cleanup; only the human-explicit `orch abandon <n> --discard` path force-removes retained work. Safe cleanup (`worktreeRemovalSafety` in `src/git/worktree.ts`, the one predicate shared by repair, runner recovery, abandon, and merge) ignores only top-level ignored paths in `cfg.disposableIgnored` (default `node_modules/`, `dist/`, `coverage/`, `logs/`); any other ignored, untracked, or dirty path keeps the worktree and is named in the retention reason, and `orch merge` reports a retained worktree instead of claiming it was pruned. If safe cleanup retains dirty, untracked, detached, or committed work—or submit state is ambiguous after a successful harness run—recovery preserves both the worktree and its claim lock for repair. A retained worktree may be reused only when Git registers its path on the expected task branch.
- **Claim setup saga** (`claimSpecific` in `src/tasks/service.ts`): setup is observe/decide/execute/compensate across the Git lock, GitHub projection, and registered worktree. Each attempt stores a unique Git-object id in its lock ref, so ambiguous writes may roll forward only after re-observing that exact owner token (or the expected issue/worktree state). Compensation restores only the saga's issue-field delta, verifies that `status:claimed` is gone, and compare-deletes only its own lock; an unverified or conflicting worktree is preserved for reconciliation.
- **Run telemetry**: every completed `processClaimed` harness run (via `processNext` or `dispatchSpecific`) appends exactly one best-effort record to `~/.orch/<project>/runs.jsonl`. Missing/malformed logs and telemetry IO errors must yield null usage or a warning without changing the task outcome. Each record carries the resolved `model` (from `resolveTaskModel`; null when unknown) so runs can be split by model/effort tier. `costUsd` prefers the harness-reported figure and only falls back to `estimateCost` (`src/board/pricing.ts`) when the log reports none — a pure per-token calc over `cfg.pricing` (per-million `{input, cachedInput, output}`; cached input billed at the cheaper cache-read rate). **Claude reports its own cost and also has built-in rates (`DEFAULT_PRICING`: opus/sonnet aliases plus the default `claude-sonnet-5-5`, keyed by `ModelSpec.model`); Codex runs under a flat subscription, so it has no pricing entry and its `costUsd` stays null by design — not a bug.** `pricing` self-heals on load (`{...DEFAULT_PRICING, ...raw.pricing}`), so a config setting only some models keeps the built-in defaults for the rest. `parseUsage` also surfaces `cachedInputTokens` (a `RunUsage`-only field feeding the cost calc; not persisted in the record).
- **Recoverable task lifecycle**: `deriveTaskState` (`src/tasks/lifecycle.ts`) is the pure authority over observed issue, lock, worktree, branch, PR, and latest unresolved telemetry facts. Its states are `ready | claimed | in-progress | in-review | needs-attention | done | inconsistent`; labels are output projections only and must never be read as lifecycle truth. Use `decideTaskTransition` before mutation, and repair every reported invariant violation before transitioning an inconsistent task. See ADR-0006.
- **Repository base branch**: `resolveBaseBranch` (`src/git/git.ts`) is the single authority for the configured `baseBranch` or GitHub-derived default. It keeps the GitHub branch name separate from its validated local/origin ref. Claim/worktree creation, runner commit detection, lifecycle reconciliation, and PR submission must use that resolution. `countCommitsAhead` requires both `merge-base` and `rev-list` to succeed; comparison failures are errors and must never be treated as zero commits.
- **Lifecycle reconciliation** (`src/tasks/reconcile.ts`): `orch repair [issue]` is read-only by default; `--apply` executes one idempotent action and then re-observes/re-plans, so interrupted or ambiguous writes resume from durable facts and repeated runs converge to no actions. Repair may restore projections/resources and safely remove only clean, attached, externally preserved worktrees; it never force-removes a worktree or deletes a branch. For a task with an open PR, repair judges the branch by the **PR head**, not the local ref: a local branch equal to or behind the PR head is tracking (its branch fact comes from the head), while one that is ahead of, diverged from, or not comparable with the head (head not fetchable) is reported as a `local-branch-matches-pr-head` violation with **no** planned actions. It never resets or fast-forwards the local branch. Destructive intent lives only at `orch abandon <issue> --discard`; plain abandon uses safe removal and retains the lock/projection when work cannot be proven safe to remove.
- **Dependency graph**: `buildGraph` (`src/board/graph.ts`) is the pure, derived DAG authority over open-issue dependencies — nothing is persisted; GitHub `Depends-on:` bodies remain source of truth. `edges` are *blocking* edges only (both endpoints open), matching `openDepsFromMap` (a dep on a closed/missing issue never blocks, so it is reported in `unresolvedDeps` instead). Cycles (deadlocked groups, from Tarjan SCC) make `topoOrder` empty; each is an ordered path (`[a,b,c]` = a→b→c→a) rendered by `formatCycle`. Three consumers share it: the runtime guard (`reportCycles` in `src/commands/cycle-report.ts`, called by `orch next`/`run` — warn-and-continue: still dispatches any eligible task, names the deadlock only when zero are eligible), `orch doctor` (cycles + closed-vs-missing dep classification via single-target `getIssue`), and the dashboard cycle banner (`Snapshot.cycles` → `#cycle-banner`). Detection is report-only — orch never auto-breaks a cycle.
- **Board projection**: `buildSnapshot` (`src/board/snapshot.ts`) is the canonical read model for open tasks and retained claim/worktree residue. Keep GitHub/Git/telemetry reads in that module and add derived board fields to its pure `assemble(...)` helper so terminal, JSON, and dashboard consumers share one mapping. `Snapshot.reviewQueue` contains PR numbers carrying `review:needed`. For GitHub deep-links the projection also carries `TaskView.prUrl` (the PR's real `html_url`, from `Pr.htmlUrl` — parsed from REST `html_url` / GraphQL `url`) and a repo-level `Snapshot.repoUrl` (one best-effort `getRepoUrl` → `gh repo view --json url`, null on failure). The dashboard builds issue links as `${repoUrl}/issues/<n>` and prefers `prUrl`, falling back to `${repoUrl}/pull/<n>`; both degrade to plain text when a URL is unknown, so a null `repoUrl` never breaks the board. `TaskView.latestRun.model` carries the run's resolved model tier (from `SnapshotRun`), and `TaskView.prChecks` (`ChecksState`: `pass|fail|pending|none|null`) is the CI roll-up — fetched via `prChecksState` **only for review-queue PRs** (issue carries `review:needed`) and memoized in a module-level `checksCache` keyed by `<cwd>:<pr>:<headSha>` with a 10-second TTL (so steady-state 2s polls reuse results, while unchanged heads and unknown SHAs still refresh). `Pr.headSha` (REST `head.sha` / GraphQL `headRefOid`) exists to key that cache. Keep `assemble` pure: it receives the checks as a `ReadonlyMap<number, ChecksState>` param; only `buildSnapshot` does the fetching.
- **Dashboard boundary**: `src/server/server.ts` serves the read routes `GET /` and `GET /status` (`/status` calls `buildSnapshot` in-process) and the write routes `POST /actions/suggest` (runs the judge in-process, writes nothing, `502` on judge failure), `POST /actions/assign` (`applyPlan`→`editIssue`, adds `assigned-by:brain` when `origin:"brain"`), `POST /actions/plan-preview` (pure `parseTickets`/`resolvePlan`, writes nothing, `400` on an invalid draft), `POST /actions/plan-create` (`createIssues`, `400` on blocking errors, otherwise returns `{created,reused,failed}`), and `POST /actions/dispatch` (validates `{issue}`, returns `202`, then calls `ServerDeps.dispatchIssue` from `setImmediate` so claim/agent work never blocks the response). `assign`, `plan-create`, and `dispatch` are the three mutating routes; suggest/plan-preview write nothing. Before handler selection or body reads, every `/actions/*` request must pass the shared authorization chokepoint: loopback peer, literal loopback `Host` on the accepting port, same-origin `Origin`, `X-Orch-Request: dashboard`, and JSON `Content-Type`; `startServer` still binds only `127.0.0.1`. Trust remains local-browser-only (the header is a CSRF/preflight signal, not a secret); a future off-box tunnel MUST add real authentication in that chokepoint first. See ADR-0004. Keep the read-route implementation and `/status` bytes stable when touching this file. `GET /status` resolves its board through the injectable `ServerDeps.snapshot` seam (defaults to `buildSnapshot`, so normal-mode bytes are unchanged); `orch serve --demo` passes a fully in-memory `ServerDeps` from `src/server/demo.ts` (including `snapshot` and a `dispatchIssue` that simulates timed `claimed → in-progress → in-review`) so the dashboard runs with no `gh`/git/`claude` — swapping only the I/O boundary, never the routes or `applyPlan`/`selectUnassigned` logic.
- **Targeted dispatch boundary**: `dispatchSpecific` (`src/tasks/runner.ts`) resolves a specific open issue from one batched `listIssues({state:"open"})`, requires a configured `agent:`, `status:todo`, and no open dependencies, then calls `claimSpecific`. Both targeted dispatch and `processNext` drive the returned `ClaimedTask` through the shared `processClaimed` finalisation path; do not fork the run/telemetry/cleanup lifecycle.
- **Effort routing boundary**: task effort is the abstract tier `easy | hard`, mapped through each adapter's `models` config to a `ModelSpec` (`{model?, effort?}`; `src/config.ts`) before invocation. Each adapter owns its flags (Claude `--model/--effort`; Codex `-m` + `-c model_reasoning_effort=`); an omitted field defers to the harness's own default. Defaults pin Sonnet 5.5 (`claude-sonnet-5-5`) for Claude and Sol 6.1 (`gpt-6.1-sol`) for Codex, both at `medium` effort for both tiers, so tiers only differ once configured. `loadConfig` merges partial specs per tier and still reads the legacy string form (a string is a model, except for Codex where it is an effort). `RunContext.model` carries the resolved spec for `runTask`; automated review (`review-run`) resolves the reviewer's spec from the same tier via `resolveTaskModel`. Telemetry `model` is `formatModelSpec` (`model@effort`), while cost lookup keys `cfg.pricing` by `spec.model`.
- **Assignment routing boundary**: plain `orch assign` emits a whole-open-graph routing brief for issues missing both `agent:` and `effort:` labels; `--apply` is fill-blanks-only and never replaces either existing routing label. Keep lead judgment external and assignment planning pure in `src/routing/assign.ts`; `--round-robin` is the legacy eligibility-gated path. Both routing writers (`orch assign` and the dashboard `POST /actions/assign`) call `ensureLabels(labelDefs(...))` (`src/github`) before `--add-label`, so a repo whose GitHub labels predate a label-set addition (e.g. `effort:*`, `assigned-by:brain`) **self-heals** instead of failing the write; `orch doctor` also flags any missing canonical labels. Label creation stays additive — never destructive.
- **Planning boundary**: `orch plan` is four modes over one pipeline. Bare `orch plan` (the default) resolves the configured lead through `makeAdapter` and requires its optional `runInteractivePlan` capability; Claude supplies that capability via `spawnInteractive` and adapter-owned argv, while unsupported adapters fail before writing with a precise `--draft` alternative. The session is seeded by the single-line `formatInteractiveSeed` (no newlines/quotes/backticks, for argv safety), writes `tickets.json`, and orch reads it back by mtime then validates with `resolvePlan`. `--draft "<goal>"` runs the fail-closed LLM planner (`runPlanner`, `src/tasks/planner.ts`) through the lead adapter's optional `runHeadless` capability. The shared `runHeadlessAgent`/`runStructuredHeadless` path owns only selection/logging/timeout mechanics; Claude and Codex own their arguments and structured JSONL reduction. `--dry-run` and create share the pure split in `src/tasks/plan.ts`: `parseTickets` (structural) → `resolvePlan` (the single validator: **errors** block creation — missing title, duplicate id; **warnings** are advisory — unknown/self dependency dropped, file-ownership overlap) → `createFromPlan` (`src/tasks/plan-create.ts`, refuses on errors and returns `{created,reused,failed}`). Creation identities are deterministic HTML comments derived from normalized plan content: every issue carries one shared plan marker and one ticket marker. A pass lists all issues once before writing, reuses markers from prior passes (including closed issues), and re-lists after any create error to reconcile response loss; it never blindly repeats an ambiguous create. Reused ticket numbers populate dependency links exactly like newly created numbers. The ticket contract lives once in the `orch-plan` skill (`assets/skills/orch-plan/SKILL.md`), inlined into `--draft` and installed by `orch init` as `/orch-plan`. `runPlanner` and `runJudge` both preserve the configured lead's `hard` model tier.
- **Judge evaluation boundary**: `evaluatePlan` (`src/routing/judge-eval.ts`) is the single definition of a *contract-valid* routing plan — `coverage-missing`, `coverage-extra`, `duplicate`, `invalid-agent`, `invalid-effort`, `missing-rationale`. It is pure (no IO/model) and shared by three consumers: the deterministic golden tests (`test/judge-eval.test.ts`), the opt-in live-model gate (`ORCH_JUDGE_LIVE=1`), and the `orch assign --judge/--auto` completeness warnings (stderr, so piped plan JSON stays clean). `applyPlan` stays the *write-time subset* — it drops malformed entries as skips but is structurally blind to a forgotten issue and to rationale quality, which is exactly what `evaluatePlan` adds. Routing *quality* (not just validity) is an offline telemetry replay, designed in ADR-0005, not implemented. See also `docs/judge.md`.

- **Operator health projection (#41)**: snapshot carries health, recoveryCommand, issueState, and open blockers; board/status/doctor/demo/dashboard use this shared projection. Shared pure task facts feed snapshot and repair. Polling lists open issues/PRs only, resolves absent issues only for retained locks/worktrees, and compares branches only for open, locked, or worktree-backed tasks. PR-history reads require a local lock, registered worktree, or local task branch and no open PR; plain todos keep `pr: "none"`. Successful bounded branch-specific and issue-reference history results (including empty results) are cached by `<cwd>:<issue>` for 60 seconds; lookup failures are inconsistent for that poll and are not cached. Completed issues with no retained claim/worktree resources are omitted. Strict lock/worktree inventory reads fail explicitly; per-task branch/registration failures are inconsistent.
- **Package verification**: the e2e package test packs a source fixture twice, checks integrity and the allowlist, and installs the tarball without install scripts. Keep prepare as the single build-before-pack hook. Run via npm run test:e2e; direct Vitest invocation may set ORCH_TEST_NPM_CLI to npm-cli.js. Documentation linked from README is shipped.

- **Self-review fallback & availability (ADR-0008)**: `detectUsageLimit` (`src/adapters/usage-limit.ts`, pure) recognises only error-shaped harness events (`error`/`turn.failed`/non-allowed `rate_limit_event`/`is_error` result), never assistant text. `src/board/availability.ts` keeps per-agent cooldowns in `~/.orch/<project>/availability.json` (`ORCH_HOME` relocates `~/.orch`; vitest sets it to a temp dir so tests never touch real state); it is runtime state and never lifecycle truth, and `processNext`/`dispatchSpecific` refuse to claim for a paused agent. `orch review-run` (`src/board/review-run.ts`) runs the reviewer through `runHeadless({readOnly:true})` (Claude `Read,Grep,Glob` with Edit/Write/Bash denied; Codex `-s read-only`), requires a fenced-JSON verdict (`parseVerdict`, fail-closed), binds it to the head it read, and records it only through the guarded `approve`/`requestChanges`. `pickReviewer` prefers any available other harness; the author's own fresh session reviews only when every other harness is on cooldown and `reviewPolicy` is `cross-or-self` (default; `cross` disables). Self records carry `mode:"self"` in the `orch-review:v1` marker; `evaluateGate` accepts the author's approval only for a marked self record under that policy, and `assertSelfReviewAllowed` refuses to write one while another harness is available.
- **Autonomous loop (ADR-0009)**: `orch autopilot` (`src/tasks/coordinator.ts`) drives tasks claim-to-merge. `decideStep` (`src/tasks/steps.ts`, pure) maps observed PR facts to one step (review/fix/resolve-conflict/merge/wait/await-human/escalate/none); `observeTasks` (`src/tasks/observe.ts`) assembles those facts (reviews via `reviewState`, CI via `prChecksState`, `prMergeability`) and skips a PR it cannot observe rather than guess. A step's result is a *signal* that wakes the loop and is appended to `~/.orch/<project>/events.jsonl`, but is never trusted as state: every pass re-derives from GitHub/Git. Executors live in `src/tasks/step-exec.ts` with an injectable `StepEnv` (agent runner + git): `executeFix` resumes the author's session (`readSession`/`writeSession`, `RunContext.resumeSession`; falls back to a fresh fully-briefed session if resume fails) and orch pushes with `HEAD:refs/heads/<branch>` (never forced), then restores `status:in-review`+`review:needed`; `executeResolveConflict` prefers Claude (`pickResolver`), merges `origin/<base>` (never rebase) and verifies the base is an ancestor before pushing; merge always goes through `merge()`/`checkMergeGate`. Round budget = max(PR change-request count, `fixRoundsFor(events)`), `cfg.maxReviewRounds` (3); exhausting it or two consecutive failed attempts escalates (`needs-attention` + PR comment) and the loop then ignores the task. A paused harness (ADR-0008) is waited out, not counted as a failure. Idle time is measured from the last real progress, not from "nothing in flight" (harness probes are not progress). Autopilot claims only issues with an explicit `agent:` label (`claimableBy` with `requireRouted`, passed via `processNext`/`claimNext`; `orch run` still takes unrouted work), `--no-claim` drives existing PRs only, and `--dry-run` lists what it would claim/skip - an unrouted issue is untriaged backlog, never consent to run it. Fix/conflict runs record `phase`/`round` in `runs.jsonl` with outcomes `fix-pushed|fix-failed|resolve-pushed|resolve-failed` (deliberately not `failed`, which lifecycle derivation treats as a failed implement run). The `Signal`/`Step` vocab is the contract: add new steps to `decideStep` and its tests first.
- **Advisory ordering (#56)**: `parseAfter` and `orderByAfter` in `src/board/board.ts` interpret `After:` separately from hard `Depends-on:` blockers. Sort only eligible candidates (and filter agent ownership before sorting in `claimNext`); unavailable predecessors never gate work. When no candidate can satisfy remaining preferences, fall back to ascending issue numbers. Targeted dispatch retains hard/lifecycle guards and ignores advisory ordering. Plans accept earlier-ticket `after` IDs; creation waits for their issue numbers to preserve references on retry. Omitted/empty `after` must not change existing v1 plan markers. Snapshot `after` references are separate from `deps`/`blockers`.
- **Review binding**: approval metadata lives in submitted COMMENT PR reviews (`src/board/approval.ts`), bound to PR/head and native review commit. Labels are projections. `review-approve --head` requires the inspected SHA; request-changes revokes earlier approvals. Merge uses the REST SHA guard and retains remote branches. Legacy labels cannot authorize a merge. Repair and snapshot derive approvals and current-head changes-requested from these records; repair removes stale approval projections and preserves the author bounce until the head changes. Snapshot caches successful open-task PR review reads by repository/PR/head for 10 seconds; repair and the merge gate always read fresh records.
